Memory: heaps, stacks and static allocation

FreeRTOS has its own allocator, separate from the C library's. Understanding that split turns “random reset after two hours” into a number you can budget.

Five heap implementations

SchemeFreesCoalescesDeterministicUse
heap_1Nevern/aYesCreate everything at boot
heap_2YesNoFragmentsDeprecated — do not use for new code
heap_3Yesvia mallocNoWhen policy requires the C allocator
heap_4YesYesYes, with coalescingDefault choice
heap_5YesYesLike heap_4RAM split across regions (TCM + SRAM)

Exactly one heap file may be linked, and it is used only for kernel objects and task stacks. Your driver's malloc calls go to the C library — a separate heap with separate failure modes. Keep it that way; mixing them is a common source of “out of memory” confusion.

printf("kernel heap: free now %u, minimum ever %u\n",
       (unsigned)xPortGetFreeHeapSize(),
       (unsigned)xPortGetMinimumEverFreeHeapSize());

The second number is the one that matters. If it approaches zero, you are one feature away from a failed xTaskCreate in the field. Keep at least 25% headroom, or move to static allocation.

Fragmentation and static allocation

heap_4 coalesces adjacent free blocks, so fragmentation is bounded but not zero: alternating allocate/free of different sizes can still split blocks over months of runtime. Two defences:

  1. Create everything at boot and never allocate again. Fragmentation cannot grow if nothing is freed.
  2. Static allocation — every object lives in .bss, sized at link time, with zero runtime allocation risk. Most safety standards require it.
/* configSUPPORT_STATIC_ALLOCATION = 1 */
static StaticTask_t xSensorTaskTCB;
static StackType_t  xSensorStack[384];

xTaskCreateStatic(vSensorTask, "sensor", 384, NULL, 4,
                  xSensorStack, &xSensorTaskTCB);

static StaticQueue_t xQueueCB;
static uint8_t xQueueStorage[16 * sizeof(SensorSample_t)];

xQueueCreateStatic(16, sizeof(SensorSample_t),
                   xQueueStorage, &xQueueCB);

With static allocation you must also supply vApplicationGetIdleTaskMemory() and, when configUSE_TIMERS is 1, vApplicationGetTimerTaskMemory(). The link fails without them — which is the point: it forces you to account for the kernel's own tasks.

void vApplicationGetIdleTaskMemory(StaticTask_t **ppxIdleTaskTCB,
                                   StackType_t **ppuxIdleStack,
                                   uint32_t *pulIdleStackSize)
{
    static StaticTask_t xIdleTCB;
    static StackType_t  xIdleStack[configMINIMAL_STACK_SIZE];

    *ppxIdleTaskTCB  = &xIdleTCB;
    *ppuxIdleStack   = xIdleStack;
    *pulIdleStackSize = configMINIMAL_STACK_SIZE;
}

Stack overflow: detection and limits

void vApplicationStackOverflowHook(TaskHandle_t xTask, char *pcTaskName)
{
    (void)xTask;
    taskDISABLE_INTERRUPTS();
    panic_log("stack overflow in %s", pcTaskName);
    for (;;) { }
}

configCHECK_FOR_STACK_OVERFLOW = 1 checks the stack pointer at each context switch (cheap, catches gross overflows). = 2 also verifies a canary at the stack's end (catches more, slightly slower). Both are development aids, not guarantees: corruption can happen before the check runs. Final sizes come from Module 4's measurement plus margin.

Watch for the silent consumers: printf with floats, snprintf of long strings, deep HAL call chains, large local arrays, and floating-point context saving on ports that do it.

Lab: find the real stack requirement

  1. Set every task to 512 words, enable check level 2, and run the full application for ten minutes with every error path exercised.
  2. Print uxTaskGetStackHighWaterMark for each task every ten seconds.
  3. Cut each stack to used + 30%, rounded up to a multiple of eight words, and re-run.
  4. Add one printf("%f") in a task and watch its high-water mark collapse.
Key takeaway

Dynamic allocation is a convenience for prototypes and a risk for products. Know which heap you are spending, measure its minimum, and decide deliberately whether the final build allocates at all.
