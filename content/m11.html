Architecture: from requirements to a task set

The API is the easy part. The design is deciding how many tasks exist, what each owns, and which one may block on what — before writing a line of code.

By the end of this module

This table answers the three questions that matter: which work is periodic, which is event-driven, and where the deadlines are. It also exposes trouble early — if the sum of worst-case work exceeds the periods, no amount of RTOS will save the design.

Decomposition heuristics

  1. One task per blocking resource. A sensor on a slow bus, a display, an SD card: each deserves an owner task that other code asks through a queue. Blocking is then contained.
  2. One task per independent rate. 1 kHz control and 1 Hz telemetry do not belong in the same loop.
  3. One task per state machine that can block. A protocol stack or UI flow is easier to read as a task with a blocking wait at the top of its loop.
  4. Do not create a task per function. Every task costs a stack (hundreds of bytes) and a context switch. Four to eight tasks covers most products.
  5. Prefer a state machine inside one task over five tasks that mostly wait on each other. Tasks are for concurrency, not for code organization.

Priorities and utilization

For periodic tasks, rate-monotonic assignment is the default: shorter period, higher priority. It is optimal among fixed-priority schemes, and it gives you a schedulability test you can do on paper:

U = sum(Ci / Ti)          /* Ci = worst-case execution, Ti = period */

U <= n * (2^(1/n) - 1)    /* n tasks: 1 task 100%, 2 tasks 82.8%,
                             3 tasks 78%, ... asymptote 69.3% */

In practice, keep total load at or below roughly 70% on a single core and leave the rest for interrupts, the tick and future features. If your table says 95%, the design is already late; simplify or move work to hardware (DMA, peripherals) before adding a faster MCU.

Priority checklist
  • Every priority has a one-sentence justification.
  • No task runs forever without blocking.
  • ISRs are shorter than every task's worst case.
  • The idle task gets measurable time (that is your CPU headroom).

Data ownership: the rule that deletes locks

Most synchronization bugs come from two writers. Fix the ownership and the locks become unnecessary:

  • Exactly one task writes a given piece of state. Everyone else requests a change through a queue or a notification.
  • Queues carry values, not shared references. If a pointer must cross a boundary, it points to a buffer owned by the receiver after the send.
  • Configuration is read-only after init. Fill it before the scheduler starts and never mutate it.
  • Hardware registers belong to one task. A register touched by two contexts needs a critical section, a mutex, or a redesign.

The gatekeeper pattern from Module 7 is the structural version of this rule: the resource has an owner, the owner has a queue, and nobody else touches the hardware.

A state machine inside a task

typedef enum { ST_IDLE, ST_MEASURE, ST_REPORT, ST_FAULT } state_t;

static void vControllerTask(void *pv)
{
    state_t eState = ST_IDLE;
    TickType_t xLast = xTaskGetTickCount();

    for (;;) {
        switch (eState) {
        case ST_IDLE:
            if (xQueueReceive(xCmdQueue, &cmd, pdMS_TO_TICKS(50))) {
                eState = (cmd == CMD_START) ? ST_MEASURE : ST_IDLE;
            }
            break;

        case ST_MEASURE:
            if (!sensor_start()) { eState = ST_FAULT; break; }
            eState = ST_REPORT;
            break;

        case ST_REPORT:
            /* Non-blocking wait keeps the loop responsive. */
            if (xSemaphoreTake(xDoneSem, pdMS_TO_TICKS(100)) == pdTRUE) {
                publish(sensor_value());
                xTaskDelayUntil(&xLast, pdMS_TO_TICKS(10));
            } else {
                eState = ST_FAULT;
            }
            break;

        case ST_FAULT:
        default:
            report_fault();
            eState = ST_IDLE;
            break;
        }
    }
}

Every state has a bounded wait, so a stuck sensor becomes a fault state rather than a frozen task. This shape — blocking wait at the top, explicit transitions, no nested loops — is what makes a task reviewable.

Anti-patterns

  • The polling loop: while (!flag) in a high-priority task. Replace with a blocking wait.
  • The god task: one task that does everything “to avoid races”. Priorities and deadlines become meaningless.
  • The shared global bus: three tasks poking the same SPI peripheral with no owner. Intermittent, unreproducible, expensive.
  • Priority inflation: raising a task's priority to fix a latency problem instead of shortening its critical section.
  • Task-per-function: twenty tasks, most of them blocked, all of them costing stack.
  • Sleep as synchronization: vTaskDelay(10) after starting a conversion, hoping it finished.

Lab: design before you code

  1. Take a product you know (a thermostat, a data logger, a robot wheel controller) and fill in the timing table for it.
  2. Propose a task list. For each task, write its owner data, its inputs, its outputs and its worst-case work.
  3. Compute utilization. If it exceeds 70%, remove a task or move work into hardware.
  4. Assign priorities with rate-monotonic ordering and write one sentence per priority.
  5. Mark every piece of shared state and name its single writer. If you cannot, the design is not finished.
Key takeaway

A good FreeRTOS design has few tasks, obvious ownership, short critical sections and a utilization number you can quote. The code then writes itself; the review is about the table.
