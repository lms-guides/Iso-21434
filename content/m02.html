Get a build running

Two tasks, two rates, no HAL delays. Get this working from scratch once and every later module becomes an experiment instead of a theory lesson.

By the end of this module

  • Choose a board and toolchain route that matches your goal.
  • Add the kernel, one port and one heap file to a project.
  • Build a two-task program and explain why each task has its own wake time.

Route D is underrated. The kernel repository contains a POSIX port under portable/ThirdParty/GCC/Posix, and the main FreeRTOS repository ships a Posix_GCC demo. Your tasks become pthreads, so queues, mutexes, notifications and timers all work, and you can printf your way through every lab in this course. It is not deterministic enough for production, but it is the fastest way to internalize the API.

Version note

Use FreeRTOS-Kernel V11.3.x for learning. For a product, start from the 202604 LTS release (kernel 11.3.0, maintained until April 2028). Both are MIT licensed. Directory names occasionally move between releases — the demo's CMakeLists.txt always names the port it uses.

What a project needs (and nothing else)

  1. Core sources: tasks.c, queue.c, list.c, plus timers.c, event_groups.c and stream_buffer.c if you use those features.
  2. Exactly one port directory for your CPU and compiler, e.g. portable/GCC/ARM_CM4F. Two ports means duplicate handler symbols.
  3. Exactly one heap file from portable/MemMang, e.g. heap_4.c.
  4. FreeRTOSConfig.h on the include path (Module 3).
  5. One interrupt priority group configured so that NVIC priority bits are usable (on Cortex-M, NVIC_PriorityGroup_4 in HAL terms).

Route A: STM32 + CubeMX, step by step

  1. Install CubeMX, CubeIDE (or CubeCLT + CMake + Ninja), and the STM32Cube firmware package for your board.
  2. New project → select the exact MCU or board, e.g. NUCLEO-F411RE.
  3. Clock tree: enable HSE/LSE as your board requires and set a known SYSCLK. Confirm SystemCoreClock matches your config value.
  4. Debug: SYS → Serial Wire. If CubeMX warns that SysTick is used by the HAL, move the HAL timebase to TIM6 — FreeRTOS needs SysTick for its own tick.
  5. UART: USART2 asynchronous, 115200 8N1, so you can retarget printf.
  6. Middleware → FREERTOS. CubeMX defaults to the CMSIS-RTOS2 wrapper. For this course, prefer the native API: either disable the wrapper and add the kernel sources yourself, or keep the wrapper and read the native calls it maps to. Learning happens in the native API.
  7. Generate with “pair of .c/.h files per peripheral”, then open Core/Src/freertos.c and read MX_FREERTOS_Init().
  8. Retarget printf to ITM_SendChar or a UART transmit. Blocking UART is fine for bring-up; Module 9 explains why it is not fine in a shared product.

Route B: ESP-IDF

idf.py create-project freertos-lab
cd freertos-lab
idf.py set-target esp32s3
idf.py menuconfig      # Component config -> FreeRTOS
idf.py build flash monitor

FreeRTOS is the native runtime, so xTaskCreate, queues and semaphores are available with no integration step. Two ESP-specific details: xTaskCreate behaves like xTaskCreatePinnedToCore(..., tskNO_AFFINITY), and the Wi-Fi stack already owns several tasks — inspect uxTaskGetSystemState early to see who shares the CPU with you.

Route C: host simulation

git clone https://github.com/FreeRTOS/FreeRTOS-Kernel.git
cd FreeRTOS-Kernel

gcc -I include -I portable/ThirdParty/GCC/Posix \
    main.c tasks.c queue.c list.c timers.c event_groups.c stream_buffer.c \
    portable/ThirdParty/GCC/Posix/port.c \
    portable/MemMang/heap_4.c \
    -lpthread -o freertos_lab

If that exact file list does not match your checkout, copy the source list from the Posix_GCC demo's build file. The point is the shape: core + one port + one heap + your main.c.

The first program

#include "FreeRTOS.h"
#include "task.h"

static void vLedTask(void *pvParameters)
{
    const TickType_t xPeriod = (TickType_t)(uintptr_t)pvParameters;
    TickType_t xLastWake = xTaskGetTickCount();

    for (;;) {
        bsp_led_toggle();
        xTaskDelayUntil(&xLastWake, xPeriod);   /* absolute period */
    }
}

int main(void)
{
    bsp_init();                                  /* clocks, GPIO, UART */

    xTaskCreate(vLedTask, "led_fast", 256,
                (void *)pdMS_TO_TICKS(100), 2, NULL);
    xTaskCreate(vLedTask, "led_slow", 256,
                (void *)pdMS_TO_TICKS(500), 2, NULL);

    vTaskStartScheduler();

    /* Only reached if the heap could not create the idle/timer task. */
    for (;;) { }
}

Notice what is absent: no while (!flag), no global tick counter, no HAL_Delay. Each task keeps its own wake time on its own stack, which is why the same function can serve both LEDs with different periods.

When the build fights back

SymptomCauseFix
undefined reference to vPortSVCHandlerPort directory not compiledAdd the matching portable/<compiler>/<arch> sources
undefined reference to pvPortMallocNo heap fileAdd exactly one of heap_1/2/3/4/5.c
Handlers defined twiceTwo ports, or startup file also defines themRemove the duplicate port; map vPortSVCHandler to SVC_Handler in the startup file
vTaskStartScheduler returnsHeap too small for idle/timer tasksRaise configTOTAL_HEAP_SIZE, add the malloc-failed hook
Board resets when the first task runsScheduler started before the FPU/clock is configuredInitialise clocks and FPU before vTaskStartScheduler()
Nothing blinks, no crashBoth tasks blocked forever, or priority 0 with the idle task runningCheck periods, priorities and that the tick is running

Lab: rebuild it cold

  1. Build and flash the two-task program. Confirm 100 ms and 500 ms blink rates with a scope or a stopwatch.
  2. Delete the project and recreate it from scratch without looking at this page. Target: under 15 minutes.
  3. Break it on purpose: remove the port directory, then the heap file, and read both linker errors.
Key takeaway

Kernel integration is three directories and one header. If you can assemble that from memory, toolchain problems stop being mysterious and start being ordinary.
