Semaphores, mutexes and priority inversion

Signalling and mutual exclusion are different problems with different objects. Using the wrong one produces bugs that only appear under load.

A binary semaphore starts empty, so the first take blocks until someone gives. A mutex starts available, so the first take succeeds. Swapping them produces “my task blocks forever at startup” or “the lock protects nothing”.

The deferred-interrupt pattern

This is the most important pattern in embedded FreeRTOS: do almost nothing in the ISR; signal a task that does the work.

static SemaphoreHandle_t xAdcReadySem;

void ADC_IRQHandler(void)
{
    BaseType_t xWoken = pdFALSE;

    adc_clear_irq();                                   /* source first */
    xSemaphoreGiveFromISR(xAdcReadySem, &xWoken);
    portYIELD_FROM_ISR(xWoken);
}

static void vAdcTask(void *pv)
{
    (void)pv;
    for (;;) {
        if (xSemaphoreTake(xAdcReadySem, portMAX_DELAY) == pdTRUE) {
            process_adc_samples();          /* may block or take 2 ms */
        }
    }
}

Use a binary semaphore when coalescing is acceptable (“something happened”). Use a counting semaphore or a queue when every event must be counted individually.

Priority inversion, concretely

The canonical failure:

  1. Low-priority task L takes mutex M.
  2. High-priority task H becomes ready and blocks on M.
  3. Medium-priority task M becomes ready and preempts L — it never touches the lock.
  4. H is now effectively waiting for a medium-priority task. If M runs long, H misses its deadline.

FreeRTOS mutexes implement priority inheritance: while H is blocked on M, L temporarily runs at H's priority, so the medium task cannot preempt it. Inheritance does not fix a bad design; it bounds the damage. The Mars Pathfinder case study is the classic account of why this matters in production.

static SemaphoreHandle_t xI2cBusMutex;

static bool i2c_read_reg(uint8_t dev, uint8_t reg, uint8_t *out)
{
    bool ok = false;

    if (xSemaphoreTake(xI2cBusMutex, pdMS_TO_TICKS(20)) == pdTRUE) {
        ok = hal_i2c_read(dev, reg, out, 1);
        xSemaphoreGive(xI2cBusMutex);
    }
    return ok;                       /* false = timeout, report it */
}

Rules for mutexes:

  • Always use a timeout in production, so a deadlock is a reported error instead of a hung product.
  • Hold for the shortest possible time. No vTaskDelay, printf, flash writes or blocking I/O while holding a lock.
  • Establish a lock order when a task needs two mutexes (for example bus-then-state), and write it down. Unordered locking is how deadlocks happen.
  • Never take a mutex in an ISR — it can block.
  • Prefer one owner per piece of data (Module 11), which removes most mutexes entirely.

Critical sections vs mutexes

taskENTER_CRITICAL();
ulSharedCounter++;
taskEXIT_CRITICAL();

/* In an ISR, if you truly must: */
UBaseType_t xSaved = taskENTER_CRITICAL_FROM_ISR();
ulSharedCounter++;
taskEXIT_CRITICAL_FROM_ISR(xSaved);

A critical section stops preemption and masks interrupts up to the syscall ceiling. It never blocks, so it cannot deadlock — but every microsecond inside it is added to the worst-case interrupt latency of the whole system. Keep them to a handful of instructions.

A mutex blocks other tasks but leaves interrupts running. Use it around longer operations and shared peripherals.

The gatekeeper pattern

When one resource — an SPI bus with three devices, an SD card, a display — is used by many tasks and each access is long, give the resource its own task and let clients send requests through a queue and wait on a reply queue. No mutex is needed: accesses are serialized by construction, and retries, timeouts and error handling live in one place. The cost is one stack and one context switch per request.

Lab: reproduce inversion, then fix it

  1. Three tasks: L (prio 1) takes a mutex then busy-waits 50 ms; M (prio 3) busy-waits 100 ms; H (prio 5) takes the same mutex and toggles a pin.
  2. Start L, then M, then H. Measure H's wait: about 150 ms.
  3. Replace the mutex with a binary semaphore used as a lock. Re-measure — inheritance is gone and M can starve H arbitrarily.
  4. Restore the mutex. H's wait drops to about 50 ms.
Key takeaway

Semaphores signal, mutexes protect. If the object is held across a long operation, redesign the ownership instead of lengthening the lock.
