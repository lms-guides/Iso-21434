Time: ticks, drift and jitter

Most “the RTOS is inaccurate” reports are a relative delay where an absolute deadline was needed. Learn the difference and measure the result.

  • vTaskDelay
  • xTaskDelayUntil
  • Tick rate
  • Jitter

By the end of this module

  • Choose between relative and absolute delays with a stated reason.
  • Pick a tick rate from resolution, CPU cost and wrap period.
  • Measure jitter instead of assuming it.

Relative vs absolute delays

vTaskDelay(n) sleeps n ticks from now. If the work in the loop takes 3 ms and the intended period is 10 ms, the real period becomes 13 ms — and the error accumulates:

loop: work 3 ms + vTaskDelay(10 ms)  ->  period 13 ms
      100 iterations = 1300 ms instead of 1000 ms  (30% slow)

xTaskDelayUntil(&last, period) sleeps until last + period, so the period stays 10 ms for as long as the work fits inside it:

TickType_t xLastWake = xTaskGetTickCount();

for (;;) {
    do_work();

    /* Returns pdFALSE if the deadline had already passed. */
    if (xTaskDelayUntil(&xLastWake, pdMS_TO_TICKS(10)) == pdFALSE) {
        g_stats.missed_deadlines++;
    }
}

Use absolute delays for every periodic task. Use vTaskDelay for timeouts and for non-periodic waits. Keep the return value: a missed deadline is a health signal, not noise.

Choosing the tick rate

TickResolutionCostUse when
100 Hz10 msLowest overheadSlow supervisory systems, battery devices
1000 Hz1 ms~1–3% CPU at 100 MHz+Default choice
10000 Hz100 µsSignificant; tick wraps in ~5 daysRare — prefer a hardware timer

Two hard limits follow from the tick. Delays shorter than one tick are impossible, so vTaskDelay(1) is the floor. And the 32-bit tick counter wraps: 49.7 days at 1 kHz. xTaskDelayUntil handles wrap correctly; code that compares raw tick values does not.

/* WRONG: breaks when the counter wraps */
if (xTaskGetTickCount() > xDeadline) { ... }

/* RIGHT: unsigned subtraction is wrap-safe */
if ((xTaskGetTickCount() - xStart) >= pdMS_TO_TICKS(500)) { ... }

Where jitter comes from

Observed wake-up jitter is the sum of three things:

  • Tick quantization — up to one full tick, because a delay expires on a tick boundary.
  • Higher-priority work — tasks and ISRs that were running when your task became ready.
  • Critical sections — time during which interrupts (and therefore the tick) are masked.

If you need better than one tick, do not raise the tick rate. Timestamp the event in a hardware-timer ISR and let the task consume timestamps; the control law then runs on real times rather than on tick counts.

Busy-waiting is a tax on every other task

/* WRONG: burns 100% CPU for 100 ms and starves everything below */
while ((xTaskGetTickCount() - t0) < pdMS_TO_TICKS(100)) { }

/* RIGHT: consumes no CPU and wakes on time */
vTaskDelay(pdMS_TO_TICKS(100));

A busy-wait inside a high-priority task is the single most common cause of “my other tasks stopped running”. If the wait is for an event rather than for time, it is worse than a bug: it is a design error. Use a queue, semaphore or notification.

Lab: measure, do not believe

  1. Toggle a GPIO at the top of a 1 kHz periodic task using xTaskDelayUntil with a one-tick period.
  2. Capture 10,000 cycles with a logic analyser or scope. Record the period and the peak-to-peak jitter.
  3. Add a 500 µs busy-wait inside a higher-priority task and re-measure. Explain each microsecond of the change.
  4. Drop configTICK_RATE_HZ to 100 and measure again. Note what happens to both resolution and CPU load.
Expected result

On a 100 MHz Cortex-M4 with no competing load, jitter should stay under roughly one tick plus 50 µs. If it does not, look for a long critical section or an ISR doing real work before blaming the kernel.

Key takeaway

Periodic means “deadline every T”, not “sleep T after finishing”. The tick sets your resolution; your critical sections set your jitter.
