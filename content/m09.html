Software timers and interrupt discipline

A timer callback is not an ISR, and an ISR is not a task. Confusing the three contexts is where intermittent, load-dependent crashes come from.

By the end of this module

Software timers

Timer callbacks execute in the context of the timer daemon task (configTIMER_TASK_PRIORITY), driven by a command queue. They are convenient for debounce, timeouts, heartbeat LEDs and periodic housekeeping.

static TimerHandle_t xLedTimer;

static void vLedCallback(TimerHandle_t xTimer)
{
    (void)xTimer;
    gpio_toggle(LED_STATUS);
}

xLedTimer = xTimerCreate("led",
                         pdMS_TO_TICKS(500),
                         pdTRUE,          /* auto-reload */
                         NULL,            /* timer ID   */
                         vLedCallback);

if (xLedTimer != NULL) {
    xTimerStart(xLedTimer, 0);
}

Useful variations:

  • xTimerChangePeriod(t, pdMS_TO_TICKS(new), 0) — change a period at runtime.
  • xTimerReset(t, 0) — restart the countdown; perfect for a “no event for 2 s” watchdog-style timeout.
  • xTimerStartFromISR, xTimerStopFromISR, xTimerResetFromISR — the only timer calls allowed from an ISR.
  • pvTimerGetTimerID() — one callback can serve several timers if it can tell them apart.
Callback rules

Callbacks must be short and non-blocking: no vTaskDelay, no queue receive with a timeout, no paragraph-sized printf. One slow callback delays every other timer in the system, including ones whose deadlines matter.

Also remember that xTimerStart is a command, not an immediate action. With a zero block time it can fail if the command queue is full — check the return value when starting timers in a burst.

ISR rules for FreeRTOS-aware interrupts

  1. Be short. Post data, set a flag, clear the source, yield. Target single-digit microseconds.
  2. Only ...FromISR APIs. xQueueSend in an ISR may block and will corrupt scheduler state.
  3. Handle pxHigherPriorityTaskWoken and call portYIELD_FROM_ISR() at the end.
  4. Never call printf, malloc, vTaskDelay, mutex operations or blocking driver code.
  5. Respect the priority ceiling. An ISR that calls any kernel API must have an NVIC priority numerically greater than or equal to configMAX_SYSCALL_INTERRUPT_PRIORITY (logically less urgent). More urgent ISRs are never masked by critical sections and must not call the kernel at all.
  6. Clear the interrupt flag. A level-triggered peripheral that is not cleared re-enters forever and starves every task. “The board resets randomly” is often this.
  7. Mind the stack. On Cortex-M without a separate ISR stack, the ISR uses the interrupted task's stack. A deep ISR call chain eats whatever task was running.
void TIM2_IRQHandler(void)
{
    BaseType_t xWoken = pdFALSE;

    if (timer_compare_flag()) {
        timer_clear_compare_flag();           /* 1. clear the source   */
        ulTimestamp = timer_read_counter();   /* 2. capture, not process */
        xQueueSendFromISR(xEdgeQueue, &ulTimestamp, &xWoken); /* 3. post */
    }

    portYIELD_FROM_ISR(xWoken);               /* 4. switch if needed   */
}

Lab: break the ISR contract three ways

  1. Call xQueueSend (the non-ISR version) from the UART ISR. Observe the assert, or the hang if asserts are disabled.
  2. Remove portYIELD_FROM_ISR. Measure the added latency with a scope: up to one full tick.
  3. Set the UART NVIC priority to 4 while the syscall ceiling is 5, then send a burst while another task is in a critical section. Explain the corruption before fixing it.
Key takeaway

ISRs capture time and data; tasks make decisions. Every millisecond of work you move out of an ISR is latency returned to the whole system.
