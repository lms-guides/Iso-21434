Tasks, priorities and stacks

Creating a task takes one call. Choosing its priority and stack size takes evidence — this module shows you how to produce that evidence.

  • xTaskCreate

By the end of this module

  • Create, suspend, resume and delete tasks correctly.
  • Assign priorities from deadlines rather than from importance.
  • Size stacks by measurement instead of guesswork.

The API you need

void vTaskSuspend(TaskHandle_t xTask);     /* NULL = self */
void vTaskResume(TaskHandle_t xTask);
BaseType_t xTaskResumeFromISR(TaskHandle_t xTask);
UBaseType_t uxTaskPriorityGet(TaskHandle_t xTask);
void vTaskPrioritySet(TaskHandle_t xTask, UBaseType_t uxNewPriority);

Rules that are not optional:

  • A task function must never return. Loop forever, or call vTaskDelete(NULL) before returning. Returning falls into no caller and is undefined behaviour.
  • pvParameters must outlive the call. Never pass the address of a local in main() that later goes out of scope, and never pass a pointer to a buffer another task mutates without synchronization.
  • Check the return value. xTaskCreate returns pdPASS or errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY. In a product, a failed creation at boot is fatal: log it and reset.
  • Names are for humans and debuggers. Short, unique names (sensor, lcd, cli) show up in vTaskListTasks and every trace tool.

Choosing priorities

A priority assignment that survives review, in order of application:

  1. Assign by deadline, not importance. The task with the tightest deadline gets the highest priority. A “critical” task that runs every ten seconds does not need priority 7.
  2. Highest: short, hard-deadline work — control loop, safety monitor, watchdog kicker.
  3. Middle: event-driven workers — protocol parsers, command handlers, UI.
  4. Lowest: soft-deadline bulk work — logging, SD writes, telemetry.
  5. Leave gaps. Use 0, 1, 2, 5, 6 rather than 0–4, so a task can be inserted later without renumbering.

More than three or four distinct levels is usually a sign that the design is unclear. Equal priorities plus time slicing are often better than a fragile eight-level hierarchy.

Starvation

A ready high-priority task prevents every lower-priority task from running. If it never blocks, nothing below it runs — not even the idle task, which means no vApplicationIdleHook and no low-power sleep. Every high-priority task must block somewhere.

Stack sizing by measurement

With configCHECK_FOR_STACK_OVERFLOW at 2, the kernel paints new stacks with a known pattern, so the unused high-water mark can be read directly:

UBaseType_t uxWordsFree = uxTaskGetStackHighWaterMark(NULL);

/* Headroom in bytes: */
size_t uxBytesFree = (size_t)uxWordsFree * sizeof(StackType_t);

The procedure:

  1. Start generous: 512 words for anything calling printf, 256 for simple logic, 128 as a floor.
  2. Run the worst case path: every branch, every error path, deepest ISR nesting, with logging enabled.
  3. Read the high-water mark. If headroom is under about 30%, add stack.
  4. Freeze the number with a comment: /* 384 words; measured 210 used, 260 worst case */.

Things that eat stack silently: printf/snprintf with float formatting (2–4 KB), malloc inside a task, deep HAL call chains, large local buffers, and floating-point context save where the port saves FPU registers.

Deleting a task without leaking

vTaskDelete(NULL) frees the task's stack and TCB only if the idle task gets to run — which is why a high-priority task that deletes itself and a starved idle task can leak memory. Two other rules:

  • Memory the task allocated with malloc is not freed for you. Either clean up before deleting, or do not use dynamic allocation in a task that can end.
  • A deleted task's handle becomes invalid immediately. Any other task holding it will corrupt the scheduler when it uses it. Prefer suspend/resume, or a supervising task that owns the lifecycle.

Lab: make preemption visible

static void vHighTask(void *p)
{
    (void)p;
    for (;;) {
        gpio_set(LED_HIGH);
        busy_wait_us(200);
        gpio_clear(LED_HIGH);
        vTaskDelay(pdMS_TO_TICKS(10));
    }
}

static void vLowTask(void *p)
{
    (void)p;
    for (;;) {
        gpio_set(LED_LOW);
        busy_wait_us(200);
        gpio_clear(LED_LOW);
        vTaskDelay(pdMS_TO_TICKS(10));
    }
}
  1. Create both at priority 2 and confirm they time-slice: both LEDs blink at 10 ms.
  2. Raise vHighTask to 3 and watch the low LED show only the leftover gaps.
  3. Remove the vTaskDelay from vHighTask and confirm the low task stops completely.
  4. Measure the high task's period with a scope, then with xTaskDelayUntil, and note the difference.
Key takeaway

A task is a deadline, a priority, a stack and an owner. If any of the four is unknown, the task is not ready to ship.
