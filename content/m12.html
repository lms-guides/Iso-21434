Debugging and instrumentation

The kernel already knows what is running, how much stack is left and how late each task is. Turn that knowledge on before you need it.

  • Asserts
  • Runtime stats
  • Trace
  • HardFault

By the end of this module

  • Use kernel instrumentation to answer “what is running, and how much stack is left”.
  • Decode a HardFault down to the offending instruction.
  • Recognize the ten classic FreeRTOS failure signatures.

First line of defence: the hooks

Before any clever tooling, make failure loud and specific:

#define configASSERT(x) \
    if ((x) == 0) { taskDISABLE_INTERRUPTS(); assert_fail(__FILE__, __LINE__); }

void assert_fail(const char *file, int line)
{
    /* Retained RAM or RTT: survives the reset you are about to do. */
    fault_log("ASSERT %s:%d", file, line);
    nvic_system_reset();
}

With asserts on, passing a NULL queue, an invalid priority or a mutex from an ISR becomes a precise file-and-line report instead of a hang. Add the stack-overflow and malloc-failed hooks from Module 10, and log to a buffer that survives reset (backup SRAM or RTT).

What is running right now

/* Requires configUSE_TRACE_FACILITY and
   configUSE_STATS_FORMATTING_FUNCTIONS. */
static char pcBuffer[1024];

vTaskListTasks(pcBuffer, sizeof pcBuffer);
printf("%s\n", pcBuffer);

/* Name  State  Prio  Stack  Num */
/* cli   B      2     118    4   */
/* sensor R     4     212    2   */
/* IDLE  R      0      92    6   */

The stack column is the high-water mark in words: the smallest free stack ever observed. A number under about 30 words is a warning; zero is a crash waiting for a slightly longer code path. vTaskGetRunTimeStatistics() adds a percentage column once runtime stats are enabled.

#define configGENERATE_RUN_TIME_STATS        1
#define portCONFIGURE_TIMER_FOR_RUN_TIME_STATS()  prvRuntimeTimerInit()
#define portGET_RUN_TIME_COUNTER_VALUE()          prvRuntimeCounter()

/* A 32-bit timer running at 10x the tick rate gives 0.1% resolution.
   Call vTaskGetRunTimeStatistics() from a low-priority task, not an ISR. */

Runtime stats answer the question “is the CPU busy, and with what?”. Idle time below ~10% means no headroom for the next feature, and a task consuming far more than its design estimate is usually polling or retrying something.

Do not underestimate the GPIO method. A pin toggled at the start of the ISR and cleared at the end of the task's work gives an unambiguous latency measurement that no tool can argue with.

Decoding a HardFault

On Cortex-M, the fault handler can read the exception frame that the hardware pushed onto the stack of the interrupted context:

void HardFault_Handler(void)
{
    __asm volatile (
        "tst lr, #4        \n"
        "ite eq            \n"
        "mrseq r0, msp     \n"
        "mrsne r0, psp     \n"
        "b hard_fault_c    \n");
}

void hard_fault_c(uint32_t *pStackFrame)
{
    uint32_t pc = pStackFrame[6];      /* stacked PC    */
    uint32_t lr = pStackFrame[5];      /* stacked LR    */
    uint32_t cfsr = *(volatile uint32_t *)0xE000ED28;
    uint32_t hfsr = *(volatile uint32_t *)0xE000ED2C;

    fault_log("HFSR %08lx CFSR %08lx PC %08lx LR %08lx",
              (unsigned long)hfsr, (unsigned long)cfsr,
              (unsigned long)pc, (unsigned long)lr);
    for (;;) { }
}

Then resolve pc with addr2line or your IDE's disassembly view. CFSR classifies the fault (usage, bus, memory management) and BFAR/MMFAR give the offending address when valid. “It crashes randomly” becomes “it dereferenced 0x00000004 at line 212”.

Test on the host too

The POSIX port from Module 2 is not only a learning tool. Pure logic — parsers, filters, state machines, protocol framing — can run under the same kernel on your laptop with mocked HAL functions, inside a normal test runner. That gives you fast, repeatable tests for the parts that do not need real hardware, while the board tests cover timing and electrical behaviour.

/* Host test sketch: feed a frame, assert the parsed result. */
void test_frame_crc_rejects_corruption(void)
{
    frame_t f = { .len = 4, .payload = {1, 2, 3, 4}, .crc = 0xDEAD };
    TEST_ASSERT_FALSE(frame_validate(&f));
}

Lab: instrument the capstone before building it

  1. Enable vTaskListTasks and print it once per second from the lowest-priority task.
  2. Enable runtime stats with a 10x tick timer and print the percentage column.
  3. Force a HardFault (dereference a bad pointer) and decode pc and CFSR to a source line.
  4. Add GPIO markers around one ISR and its task, and measure the end-to-end latency with a scope.
Key takeaway

Do not debug a scheduler by guessing. Asserts name the error, the task list names the state, runtime stats name the cost, and the stacked PC names the instruction.
