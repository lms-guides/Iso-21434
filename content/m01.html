Why an RTOS at all

Before the API, the mental model. FreeRTOS does not make code faster; it makes response time a property you can design, measure and defend.

The superloop, and where it breaks

Almost every embedded project starts like this:

int main(void)
{
    bsp_init();

    for (;;) {
        read_sensor();       /* 2 ms  */
        update_display();    /* 30 ms */
        handle_uart();       /* 1 ms  */
        delay_ms(10);        /* period is 43 ms, not 10 */
    }
}

Three structural problems appear as soon as the product grows, and none of them can be fixed by writing the functions better:

  1. Latency is the sum of everything else. A UART byte waits up to 43 ms. Add a feature and every existing response gets slower.
  2. Blocking is contagious. One delay_ms(500) inside a driver stalls the display, the protocol and the watchdog.
  3. No composition. update_display() cannot be reused in a second product with a different timing profile, because its timing is baked into the loop order.

You can fix these with hand-written state machines and timer interrupts — plenty of shipping products do — but you end up re-implementing a scheduler, a queue and a timeout mechanism, with no tests and no documentation.

What the kernel actually adds

  • Tasks — independent execution contexts, each with its own stack, that appear to run concurrently on a single core.
  • Preemption — a higher-priority ready task runs immediately, even in the middle of a lower-priority function.
  • Blocking primitives — a task waiting for data consumes no CPU and wakes on the event or the timeout.
  • Priority-based determinism — the highest-priority ready task always runs, so worst-case latency becomes a design property instead of luck.

That last point is the real reason to use an RTOS. Throughput is a pleasant side effect; bounded response time is the product.

The scheduler in one paragraph

Every task is in exactly one state: Running (one per core), Ready, Blocked (waiting for time or an event, with an optional timeout), Suspended (parked explicitly, no timeout), or Deleted. The scheduler always runs the highest-priority ready task. On a tie, ready tasks at the same priority take turns one tick each when configUSE_TIME_SLICING is 1.

The tick — SysTick on Cortex-M — increments a counter and drives timeouts. The actual context switch happens in the PendSV exception, which is configured to the lowest interrupt priority so it never preempts a real ISR.

Priority convention

In FreeRTOS a numerically higher priority is more urgent, and priority 0 belongs to the idle task. This is the opposite of ARM NVIC interrupt priorities, where a lower number preempts. Mixing the two conventions up is the most common first-week bug.

What FreeRTOS is not

  • No processes, no MMU isolation by default, no protection between tasks. A bad pointer in one task corrupts another. MPU ports exist, but they are a deliberate design choice.
  • No file system, TCP/IP stack, USB stack or CLI in the kernel. FreeRTOS-Plus-TCP, coreMQTT and littlefs are libraries that use the kernel.
  • Not a hard real-time guarantee by itself. The kernel gives you the mechanism; your interrupt priorities, critical sections and allocation strategy decide whether you get the guarantee.

Where the code lives

FreeRTOS-Kernel/
  tasks.c  queue.c  list.c  timers.c  event_groups.c  stream_buffer.c
  include/                  FreeRTOS.h, task.h, queue.h, semphr.h, timers.h
  portable/
    MemMang/heap_1.c ... heap_5.c
    GCC/ARM_CM4F/           port.c, portmacro.h  (Cortex-M4F)
    GCC/ARM_CM33_NTZ/       Cortex-M33
    ThirdParty/GCC/Posix/   host simulation

A project adds exactly three things: the core .c files, one port directory, and one heap implementation. Knowing that makes “undefined reference to xQueueGenericSend” and “vPortSVCHandler multiply defined” trivial to diagnose.

Five-minute lab

  1. Read your current project's main loop. Write down the worst-case time from “UART byte arrives” to “byte is processed”. That number is your baseline.
  2. List the independent activities in the loop and their periods. If two of them have no reason to be in the same loop, they are your first two tasks.
  3. Name the deadline of each. Not the period — the deadline. That list becomes the priority order in Module 4.
Key takeaway

An RTOS buys you concurrency and blocking, so that response time can be reasoned about per activity. If you cannot name the deadline of a task, you are not ready to give it a priority.
