Shipping: hardening and release checklist

A demo survives a bench session. A product survives a year of brown-outs, a stalled sensor and a firmware update in the field.

By the end of this module

Watchdog design

The independent watchdog is the only mechanism that recovers from a corrupted heap, a deadlock or a task that silently stopped. Use it as a supervisor, not as a formality:

  • One feeder. A single health task refreshes the watchdog, and only after every supervised task has reported a heartbeat.
  • Timeout from the requirement. If the product must recover within 5 s, a 2 s watchdog plus reset time fits; pick the number deliberately.
  • Feed late, not early. Feeding at the top of the loop before the work means a hang after the feed still resets; feeding after the work means a slow iteration can reset a healthy system. Choose per task and document it.
  • Log before reset. A fault record in backup SRAM or RTT tells you why the next boot happened.
  • Test it. Add a debug command that blocks a task on purpose and confirm the reset and the log.
/* Boot: report the previous reset cause, then clear it. */
reset_cause_t cause = reset_cause_read();

if (cause == RESET_WATCHDOG) {
    fault_log_dump();          /* print the retained fault record */
    g_stats.watchdog_resets++;
}
reset_cause_clear();

Error handling that scales

Asserts are for programmer errors — a NULL queue, an impossible state. They should not handle a sensor that is merely absent. Use three tiers:

TierExampleResponse
Expected errorI2C NAK, CRC mismatchRetry with backoff, count, continue
Degraded operationSD card removedBuffer to RAM, set a fault flag, keep sampling
Programmer errorNULL handle, invalid priorityAssert, log, reset

Return codes are not enough on their own: a caller that ignores them turns a recoverable error into a silent one. Either handle it, or log it and propagate it. A global fault bitmap plus a counter per fault class is enough for most products, and it makes the CLI's status command genuinely useful.

Power and the tick

If the product is battery powered, idle time becomes a design target:

  • Tickless idle (configUSE_TICKLESS_IDLE) lets the kernel sleep until the next real deadline instead of waking every tick. It needs a low-power timer the port can use, and it changes timing behaviour — test it, do not assume it.
  • WFI in the idle hook is the cheap version: sleep until the next interrupt, keep the tick.
  • Turn peripherals off in the lowest-priority task, not in the idle hook, if the ordering matters.
  • Measure. A multimeter in series with the board over 60 s beats any estimate. Compare run, idle and sleep currents and compute the expected battery life from the duty cycle.

Firmware update and rollback

An A/B scheme with a bootloader gives you the recovery path that a watchdog alone cannot:

  1. Two slots — the running image and the candidate. The bootloader selects by a version/validity record.
  2. Confirm after self-test. The new image marks itself valid only after passing its own checks (peripherals, storage, network). Until then, a reset returns to the previous slot.
  3. Sign and verify. A/B gives rollback, not authenticity. Check the image signature and version before booting it.
  4. Preserve state across the update: configuration and calibration live in a separate region, with a schema version.

Testing strategy

LayerRuns onCovers
Unit testsHost + POSIX port, mocked BSPFilters, parsers, state machines, framing
IntegrationBoard, scriptedTask interactions, queue depths, CLI
TimingBoard + scope/analyserLatency, jitter, ISR duration, priority behaviour
Fault injectionBoardStalled task, full queue, I2C NAK, SD removal, brown-out
SoakBoard24–72 h: heap minimum, stack watermarks, counters

The POSIX port makes the first layer cheap: the same kernel, the same tasks, but tests run in a second on a laptop and in CI. Keep the BSP narrow so the mock is small.

Release checklist

  • All asserts kept in the release build, or replaced by logged resets — never silently compiled out.
  • Stack high-water marks ≥ 30% free on every task after the soak, with logging enabled.
  • Kernel heap minimum ≥ 25% free, or fully static allocation.
  • Idle time ≥ 10% under worst-case load; runtime stats captured and archived.
  • Every ISR calls only FromISR APIs and sits at or below the syscall priority ceiling.
  • Every mutex take has a timeout; every queue send has a documented full policy.
  • Watchdog tested by injection, with reset cause and fault log verified across reboot.
  • Brown-out and power-cycle recovery verified with the storage mounted.
  • Compiler warnings clean at -Wall -Wextra; static analysis run on the application code.
  • Version string, git SHA and build date readable from the CLI or a status register.
  • No printf in an ISR or a timer callback; no blocking call while holding a lock.
  • Recovery procedure documented: how to enter the bootloader, how to roll back.
Certification, if you need it

FreeRTOS is MIT-licensed and widely used, but a safety certificate is a property of a specific integration, not of the source. For IEC 61508, ISO 26262 or DO-178C work, look at the safety-certified derivatives and partner offerings (for example SAFERTOS), plus the kernel's MISRA compliance documentation. Budget for the evidence, not just the code.

Where to go next

  • Read the kernel source. tasks.c and queue.c are readable in an afternoon and explain every behaviour in this course.
  • Read the FreeRTOS-Kernel Book for the design rationale behind queues, scheduling and the timer daemon.
  • Build the capstone on real hardware, then add one hard feature: a TCP telemetry link, a bootloader, or an MPU-protected task.
  • Try an SMP port (RP2040 or a dual-core Cortex-M) to see what changes when two cores run the scheduler at once.

Final lab: your own checklist

  1. Take your current project and score it against the twelve release items. Be honest.
  2. Fix the two cheapest failures this week. Measure again.
  3. Write the memory and CPU budget into the repository, with the measurement date.
  4. Run a 24-hour soak and keep the log as the baseline for the next release.
Key takeaway

Shipping is mostly remembering: keep the asserts, measure the margins, name the faults, and make recovery a tested path rather than a hope. That is the whole difference between “it works on my desk” and a product.
